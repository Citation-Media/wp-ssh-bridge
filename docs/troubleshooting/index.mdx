---
title: Troubleshooting
description: The failures people actually hit with wp-ssh-bridge, what causes them, and the smallest change that fixes each one.
---

Start with the exact error text. The CLI names the failing stage and, where it can, the path or value that caused it. The tables below map the common messages to a fix.

## SSH and connectivity

| Symptom | Cause | Fix |
| --- | --- | --- |
| `Permission denied (publickey)` | The host does not accept the key OpenSSH offered. | Test `ssh <destination>` first; see [SSH access](/docs/ssh-access#when-a-connection-fails). |
| `Host key verification failed` | The host is not in `known_hosts`. | Connect once with `ssh <destination>` and accept the key. |
| The SSH agent asks for approval several times in one run | A direct `pull`, `push`, or `clone` authenticates once per login, so repeated prompts there mean the installed binary predates connection sharing. With the DDEV provider, each step such as `db-pull` and `files-pull` is its own process and asks once, which is expected. | For direct runs, [update wp-ssh-bridge](/docs/installation#updating). See [One connection per run](/docs/ssh-access#one-connection-per-run). |
| Connection times out | Wrong port or a firewall. | Put the port into the destination, `deploy@host:2222`, or add a `Host` block in `~/.ssh/config` and use the alias as the destination. |
| `the destination already carries the user, host, and port` | A destination and `pull_user`, `pull_host`, or `pull_port` were set in the same place, or split values from an environment variable or flag were set over a config that uses `pull_destination`. | Remove the split values or move them into the destination. A destination override over a split-form config is fine. |
| The host is only reachable through a bastion or a client such as Teleport | Plain `ssh host` cannot reach it. | Put `ProxyJump` or the client's `ProxyCommand` into a `Host` block, as that tool documents, and use the alias as the destination. |
| `Fatal: remote WordPress path does not exist: <path>` | The remote WordPress root is wrong. | `pull_remote_path` or `push_remote_path` must be absolute and contain `wp-config.php`. |

:::note[Private keys stay out of the CLI]
There is no key or password option, by design. Configure access in `~/.ssh/config`, your agent, or an identity file, exactly as for any other SSH client. Password managers such as 1Password, Bitwarden, and Proton Pass work as agents once set up as their own documentation describes; [SSH access](/docs/ssh-access) covers what the CLI expects.
:::

## WP-CLI and the database

| Symptom | Cause | Fix |
| --- | --- | --- |
| `WP-CLI not found or unusable; downloading wp-cli.phar to <path>` | The host has no working `wp`. | Nothing to do: the phar is downloaded to the remote temp directory and kept there for later runs. The run only fails if the host has neither `curl` nor `wget`, or the phar cannot execute, directly or through `php`. |
| `mariadb-dump: command not found` | A MariaDB host that ships only the legacy client names. | [Update wp-ssh-bridge](/docs/installation#updating); current versions alias the names during preflight. If the compatibility line appears and the export still fails, the host lacks `mysqldump` too. See [Netcup and MariaDB clients](/docs/troubleshooting/netcup-mariadb). |
| The export fails with `exit status 255` and no message | The host disables PHP's `exec()`, which `wp db export` needs. | Handled automatically on current versions. See [Disabled PHP functions](/docs/troubleshooting/disabled-php-functions). |
| `PHP function check failed` or `does not allow re-enabling them` | The export needs a PHP function the host disables, and the CLI cannot confirm or apply the per-command override. | See [When something fails](/docs/troubleshooting/disabled-php-functions#when-something-fails). |
| `Fatal: remote temporary directory is not writable: <path>` | `/tmp` is restricted on the host. | Point `pull_remote_tmp_dir` or `push_remote_tmp_dir` at a writable directory inside the account. |
| `the push target uses the table prefix …, but the local database uses …` | The target's `wp-config.php` names another `$table_prefix` than your local copy, so its WordPress would not see the pushed tables. Nothing was changed. | Set `$table_prefix` in the target's `wp-config.php` to the local prefix, or pull from that target first so the local copy takes its prefix. |
| WordPress shows the installer after a pull, or a warning names `$table_prefix` | The source uses another table prefix, and the CLI could not change the local one: `wp-config.php` has no `$table_prefix` line, as in Bedrock, or another file overrides it. | Set the prefix from the warning where your config defines it. Check it with `wp config get table_prefix`. |
| The import fails halfway | Usually a database size or timeout limit. | Try `--skip-files` to isolate the database step, and check the remote error in full. |

## Local files

| Symptom | Cause | Fix |
| --- | --- | --- |
| `local WordPress files are not writable at <path>` | Ownership or permissions on the local WordPress directory. | The error prints the path and, on Linux and WSL, the `chown` command that fixes it. |
| `local WordPress path <path> is outside the wp-env tree` | `local_wp_path` points outside the mounted tree, so files and WP-CLI would target different installations. | Clear `local_wp_path` and let wp-env report the root. |
| Files pulled but the site does not see them | In wp-env, a bind mount is shadowing the pulled path. | Expected. Those paths are excluded; see the wp-env section below. |

## Transports

| Symptom | Cause | Fix |
| --- | --- | --- |
| `scp/tar transport: stale local files not removed (no --delete equivalent)` | rsync is missing on one side, so the tar-over-SSH fallback is in use. | Install rsync on both machines, or accept that deleted files remain. |
| Transfers are slow on a large site | Media is being copied. | Leave `clone_images` off for day-to-day pulls; you rarely need production uploads to write code. |
| You want to reproduce the fallback | Debugging a transport issue. | Force it with `--force-scp`. |

## Runtime detection

| Symptom | Cause | Fix |
| --- | --- | --- |
| `integration is pinned to wp-env, but no .wp-env.json was found above the working directory` | A strict pin that cannot be resolved. | Remove the pin, or run from the correct project root. The strictness is the point: it prevents syncing into the wrong local WordPress root. |
| The CLI picked the wrong runtime | The repository carries markers for two runtimes. | Pin it: `integration: "ddev"` in the config, or `--integration ddev` for one run. |
| `ddev describe failed` | The project is not started. | `ddev start`, then run again. |
| `no DDEV, wp-env, or configured standalone project found; run from the project root or pass --project-root` | `plugins remove` ran outside a project: no DDEV or wp-env marker, and no `.wp-ssh.yaml` in the working directory. | Run it from the project root, or pass `--project-root`. |

## wp-env

| Symptom | Fix |
| --- | --- |
| `wp-env environment is "stopped"` | Run `wp-env start`, then retry. |
| `wp-env is using the "playground" runtime` | Playground has no `wp-env run`. Restart with `wp-env start --runtime=docker`. |
| `wp-env status failed` | Run from the wp-env project root and make sure wp-env is installed, either as a project dependency, on `PATH`, or reachable through `npx`. |
| ``this is a wp-env project but `wp-env status --json` did not succeed`` | Start or install the environment. Do not reach for `--integration standalone` as a workaround for anything that leads to a push; see below. |
| `push does not support wp-env projects` | Expected and deliberate. Push from a standalone checkout instead; see [Push](/docs/commands/push). |
| A warning about mounted plugins or themes before a pull | Expected. Those paths are excluded because the mounts would shadow them. Use `--skip-files` for a database-only sync. |
| A plugin disappeared after a pull | Production-only tooling is removed by design. [Blocked plugins](/docs/troubleshooting/blocked-plugins) lists every slug and explains the three cases where nothing is removed. |

:::tip[Make wp-env runs faster]
When wp-env is resolved through `npx`, the package is looked up on every invocation, which roughly doubles startup time. Add it as a dev dependency instead:

```bash
npm install --save-dev @wordpress/env
```
:::

## DDEV

| Symptom | Fix |
| --- | --- |
| `.ddev/bin/wp-ssh-bridge: No such file or directory` during a provider callback | The project-local binary is missing. Reinstall it with the install script, then run `./.ddev/bin/wp-ssh-bridge provider install`. |
| A `node_modules/…/wp-ssh-bridge` path is missing during a provider callback | The provider files were generated by a CLI installed with npm, and `node_modules` is not installed in this checkout. Run `npm install`. |
| The provider calls a binary you no longer use | The provider files still point at the binary from before you changed how the CLI is installed. Run `provider install` again with the binary you use now, or pass `--binary` with the path the provider should call. |
| `ddev pull wp-ssh --destination deploy@host` is rejected | Native DDEV pull takes no CLI flags. Use `--environment=WP_SSH_PULL_DESTINATION=deploy@host` instead. |
| Local multisite domains do not resolve | Either a mapping is missing, or DDEV has not picked up the new hostnames. Add missing mappings with `domains add`, which also refreshes `additional_hostnames` and the provider files, then run `ddev restart`. |
| The provider behaves oddly after an update | Regenerate it: `./.ddev/bin/wp-ssh-bridge provider install`, or `npx wp-ssh-bridge provider install` when you installed with npm. |

## URLs after a pull or push

| Symptom | Cause | Fix |
| --- | --- | --- |
| The site still shows the production domain | Search-replace was skipped, or no mapping is configured. | Check `skip_search_replace` and `pull_domain_replacements`. |
| Some multisite subsites point at production | Only the main domain is mapped. | Add a mapping per subsite domain, protocol-less. |
| Redirects to production on every request | A hard-coded constant in `wp-config.php` survived. | The post-pull step rewrites `WP_HOME`, `WP_SITEURL`, and `DOMAIN_CURRENT_SITE`. If a plugin or a `sunrise.php` sets its own, handle that file by hand. |
| `the push target URL is unknown because it could not be read from the target` | The target has no installed WordPress site yet, typically on a first push into an empty target, so there is no home URL to replace the local one with. | Set `push_url`, `WP_SSH_PUSH_URL`, or `--push-url`, or add a push domain mapping. To keep the local URLs on purpose, pass `--skip-search-replace`. See [Migrate a site](/docs/migrate-a-site) for a complete move. |
| The target shows the wrong URL after a push | Without `push_url`, the push reuses the home URL the target had before the import, which was not the URL you wanted. | Set `push_url`, then rerun the push with `--skip-files`. |

## Command names after the rename

The `migrate` command became [`clone`](/docs/commands/clone).

| Symptom | Fix |
| --- | --- |
| `unknown command "clone"` | The binary predates the rename. [Update it](/docs/installation#updating). |
| `the "migrate" command was renamed to "clone"` | Use `wp-ssh-bridge clone` with the same flags. |
| `unknown config key "migrate_db_host"` | Rename `migrate_db_*` keys to `clone_db_*`. |
| Target DB credentials reported as missing | `WP_SSH_MIGRATE_DB_*` variables are ignored silently. Rename them to `WP_SSH_CLONE_DB_*`. |

## Still stuck

Collect these before asking for help; they answer most follow-up questions immediately:

```bash
wp-ssh-bridge version
```

```bash
# The exact failing command, without --silent so prompts and output are visible
wp-ssh-bridge pull
```

Then note which runtime you are in, whether rsync is available on both sides, and the full error text rather than a summary of it.
