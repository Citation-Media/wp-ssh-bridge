wp-ssh-bridge has exactly one real secret, `clone_db_password`. Everything else it needs is configuration: an SSH address, a remote path, a URL. Two kinds of those still belong in a secrets manager rather than in Git: values that differ per environment, such as a staging target you would rather not commit next to production, and values that differ per developer.

The CLI does not talk to any secrets manager. It has [env mode](/docs/configuration): every key has a `WP_SSH_*` variable, and environment variables override the config file. A secrets manager's only job is to put those variables into the process environment for one run, and 1Password, Bitwarden, and Proton Pass each have a command for exactly that:

```bash
op run --env-file=wp-ssh.env -- wp-ssh-bridge pull --silent        # 1Password
bws run --project-id <project> -- wp-ssh-bridge pull --silent      # Bitwarden Secrets Manager
pass-cli run --env-file=wp-ssh.env -- wp-ssh-bridge pull --silent  # Proton Pass
```

The same managers can also hold the **SSH key** a pull authenticates with. That is a separate mechanism, an SSH agent, and it needs nothing from the CLI; see [SSH access](/docs/ssh-access). The two combine: the agent signs the connection, the injected variables say where it goes.

## What goes into the secrets manager

Split by what the value is, not by where it is used. Where a value lives inside the manager is the manager's business: in 1Password and Proton Pass that is an item in a vault, in Bitwarden a Secrets Manager project, and each tab below uses the one that fits.

| Belongs in the secrets manager | Stays in the committed config |
| --- | --- |
| `WP_SSH_PULL_DESTINATION`, the source address, when it differs per environment or per developer | `local_wp_path`, the domain replacements, `plugin_remove_file`, `clone_images` |
| `WP_SSH_PUSH_DESTINATION`, `WP_SSH_PUSH_URL`, the target, when the team should not be able to push from any checkout | `pull_remote_path` and `push_remote_path`, unless they differ per environment too |
| `WP_SSH_CLONE_DB_PASSWORD`, always, and the other `WP_SSH_CLONE_DB_*` values with it | `integration`, `provider` |

Use one destination per target, in any of the [address forms](/docs/ssh-access#one-address-instead-of-three-values). Do not add `WP_SSH_PULL_USER`, `WP_SSH_PULL_HOST`, or `WP_SSH_PULL_PORT` beside it: a destination already carries those, and the CLI rejects the combination rather than guessing which one wins.

:::note[A ~/.ssh/config alias may be all you need]
If the only per-developer value is the SSH user, a committed `pull_destination: "prod"` plus a `Host prod` block in each developer's `~/.ssh/config` solves it without a secrets manager. Reach for one when there is a real secret, or when the address itself must not be committed.
:::

## Injecting the values

<Tabs inline param="manager" syncKey="manager">
  <Tab title="1Password">

    1Password CLI reads **secret references**, `op://<vault>/<item>/<field>`, and resolves them at run time. Keep the references in an env file; it contains no secrets, so it can be committed:

    ```text title="wp-ssh.env"
    WP_SSH_PULL_DESTINATION=op://Infrastructure/production-wordpress/ssh_destination
    WP_SSH_PULL_REMOTE_PATH=op://Infrastructure/production-wordpress/remote_path
    WP_SSH_CLONE_DB_PASSWORD=op://Infrastructure/target-database/password
    ```

    ```bash
    op run --env-file=wp-ssh.env -- wp-ssh-bridge pull --silent
    ```

    `op run` starts the command as a subprocess with the resolved values in its environment, for that process only, and masks them if they ever appear on stdout or stderr. Nothing is exported into your shell.

    1Password Environments, which keep such a variable set inside 1Password instead of a file, are still in beta. They plug into the same command (`op run --environment <id>`), so nothing here changes once they are generally available.

  </Tab>
  <Tab title="Bitwarden Secrets Manager">

    Secrets Manager stores secrets per **project** and reads them with a **machine account** token. Name each secret exactly like the variable, because `bws run` exports secret names as variable names:

    | Secret name | Value |
    | --- | --- |
    | `WP_SSH_PULL_DESTINATION` | `deploy@production.example.com:2222` |
    | `WP_SSH_PULL_REMOTE_PATH` | `/home/production/public_html` |
    | `WP_SSH_CLONE_DB_PASSWORD` | the target database password |

    Give the machine account read access to the project, then:

    ```bash
    export BWS_ACCESS_TOKEN="0.48c7…"          # the machine account token, from Secrets Manager
    bws run --project-id <project-id> -- wp-ssh-bridge pull --silent
    ```

    `bws secret list <project-id> --output env` shows what the run will see. Keep `--project-id` on the command: without it, every secret the machine account can reach becomes a variable, and unrelated `WP_SSH_*` names from another project would win over your config file.

    Two things to avoid here. `--no-inherit-env` starts the command with an empty environment, which drops `PATH` and `SSH_AUTH_SOCK`, so the agent that signs the SSH connection disappears with it. And `bws run` does not mask secret values in output, so keep `--silent` on and do not print the environment from scripts.

  </Tab>
  <Tab title="Proton Pass">

    Proton Pass CLI works like 1Password's: it reads **secret references**, `pass://<vault>/<item>/<field>`, from an env file or from the shell environment and resolves them at run time. The file holds no secrets, so it can be committed:

    ```text title="wp-ssh.env"
    WP_SSH_PULL_DESTINATION=pass://Infrastructure/production-wordpress/ssh_destination
    WP_SSH_PULL_REMOTE_PATH=pass://Infrastructure/production-wordpress/remote_path
    WP_SSH_CLONE_DB_PASSWORD=pass://Infrastructure/target-database/password
    ```

    ```bash
    pass-cli login                                                     # once; the session persists until pass-cli logout
    pass-cli run --env-file=wp-ssh.env -- wp-ssh-bridge pull --silent
    ```

    `pass-cli run` starts the command as a subprocess with the resolved values in its environment and masks them in stdout and stderr as `<concealed by Proton Pass>`; `--no-masking` turns that off for debugging. `--env-file` may be repeated, later files overriding earlier ones, which is one way to layer a shared file and a per-environment one.

    For scripts that cannot log in interactively, Proton Pass has personal access tokens (`pass-cli pat`); their sessions last two hours and are the recommended route for automation.

  </Tab>
</Tabs>

## DDEV and wp-env

Nothing changes. The DDEV provider commands run on the host, so they see the environment of the `ddev pull` process, and wp-env projects run the CLI directly:

```bash
op run --env-file=wp-ssh.env -- ddev pull wp-ssh -y
bws run --project-id <project-id> -- npx wp-ssh-bridge pull --silent
pass-cli run --env-file=wp-ssh.env -- ddev pull wp-ssh -y
```

## Several environments

Give each target its own env file or project, and keep everything they share in the config file:

```bash
op run --env-file=wp-ssh.production.env -- wp-ssh-bridge pull --silent
op run --env-file=wp-ssh.staging.env    -- wp-ssh-bridge pull --silent
```

Where the variants hold no secrets at all, `--config-file .wp-ssh.staging.yaml` does the same job without a secrets manager; see [several sites in one repository](/docs/configuration#monorepo) for the layout.

## When it does not work

| Symptom | Cause |
| --- | --- |
| `the destination already carries the user, host, and port` | The secrets manager sets `WP_SSH_PULL_DESTINATION` while the config file, another variable, or a flag still sets `pull_user`, `pull_host`, or `pull_port`. Keep one form. |
| `Permission denied (publickey)` under `bws run` | `--no-inherit-env` removed `SSH_AUTH_SOCK`. Drop the flag. |
| A value shows as `<concealed by 1Password>` or `<concealed by Proton Pass>` | Expected: `op run` and `pass-cli run` mask secrets they injected. Use `--no-masking` only while debugging. |
| The run prompts for a value | The variable is missing from the env file or project, and the command ran without `--silent`, so `init`-style prompts appeared. Check the file or `bws secret list --output env`, and keep `--silent`. |
| The wrong environment was pulled | Two env files or projects both define `WP_SSH_PULL_DESTINATION`. Pass exactly one `--env-file` or `--project-id`. |
