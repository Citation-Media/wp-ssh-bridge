wp-ssh-bridge has exactly one real secret, `clone_db_password`. Everything else it needs is configuration: an SSH address, a remote path, a URL. Two kinds of those still belong in a vault rather than in Git: values that differ per environment, such as a staging target you would rather not commit next to production, and values that differ per developer.

The CLI does not talk to any vault. It has [env mode](/docs/configuration): every key has a `WP_SSH_*` variable, and environment variables override the config file. A secrets manager's only job is to put those variables into the process environment for one run, and both 1Password and Bitwarden have a command for exactly that:

```bash
op run --env-file=wp-ssh.env -- wp-ssh-bridge pull --silent      # 1Password
bws run --project-id <project> -- wp-ssh-bridge pull --silent    # Bitwarden Secrets Manager
```

The same managers can also hold the **SSH key** a pull authenticates with. That is a separate mechanism, an SSH agent, and it is covered on [SSH access](/docs/ssh-access#password-managers-as-ssh-agents). The two combine: the agent signs the connection, the injected variables say where it goes.

## What goes into the vault

Split by what the value is, not by where it is used:

| Belongs in the vault | Stays in the committed config |
| --- | --- |
| `WP_SSH_PULL_DESTINATION`, the source address, when it differs per environment or per developer | `local_wp_path`, the domain replacements, `plugin_remove_file`, `clone_images` |
| `WP_SSH_PUSH_DESTINATION`, `WP_SSH_PUSH_URL`, the target, when the team should not be able to push from any checkout | `pull_remote_path` and `push_remote_path`, unless they differ per environment too |
| `WP_SSH_CLONE_DB_PASSWORD`, always, and the other `WP_SSH_CLONE_DB_*` values with it | `integration`, `provider` |

Use one destination per target, in any of the [address forms](/docs/ssh-access#one-address-instead-of-three-values). Do not add `WP_SSH_PULL_USER`, `WP_SSH_PULL_HOST`, or `WP_SSH_PULL_PORT` beside it: a destination already carries those, and the CLI rejects the combination rather than guessing which one wins.

:::note[A ~/.ssh/config alias may be all you need]
If the only per-developer value is the SSH user, a committed `pull_destination: "prod"` plus a `Host prod` block in each developer's `~/.ssh/config` solves it without a vault. Reach for a secrets manager when there is a real secret, or when the address itself must not be committed.
:::

## Injecting the values

<Tabs inline param="manager" syncKey="manager">
  <Tab title="1Password">

    1Password CLI reads **secret references**, `op://<vault>/<item>/<field>`, and resolves them at run time. Keep the references in an env file; it contains no secrets, so it can be committed:

    ```text title="wp-ssh.env"
    WP_SSH_PULL_DESTINATION=op://Infrastructure/production-wordpress/ssh_destination
    WP_SSH_PULL_REMOTE_PATH=op://Infrastructure/production-wordpress/remote_path
    WP_SSH_CLONE_DB_PASSWORD=op://Infrastructure/target-database/password
    ```

    ```bash
    op run --env-file=wp-ssh.env -- wp-ssh-bridge pull --silent
    ```

    `op run` starts the command as a subprocess with the resolved values in its environment, for that process only, and masks them if they ever appear on stdout or stderr. Nothing is exported into your shell.

    **1Password Environments** move the whole variable set into 1Password instead of a file, which is what you want when several people share it. In the desktop app, open **Developer › View Environments**, create one, and import `wp-ssh.env` or add the variables by hand. Then copy its ID from **Manage environment › Copy environment ID** and run:

    ```bash
    op run --environment <environment-id> -- wp-ssh-bridge pull --silent
    ```

    `op environment read <environment-id>` prints the variables as `KEY=value` lines when you need to check what the run will see. Environments need the beta CLI, `2.33.0-beta.02` or later; an Owner or Administrator has to enable the policy once. An Environment can be combined with `--env-file` and with variables already in your shell, and takes precedence over both.

  </Tab>
  <Tab title="Bitwarden Secrets Manager">

    Secrets Manager stores secrets per **project** and reads them with a **machine account** token. Name each secret exactly like the variable, because `bws run` exports secret names as variable names:

    | Secret name | Value |
    | --- | --- |
    | `WP_SSH_PULL_DESTINATION` | `deploy@production.example.com:2222` |
    | `WP_SSH_PULL_REMOTE_PATH` | `/home/production/public_html` |
    | `WP_SSH_CLONE_DB_PASSWORD` | the target database password |

    Give the machine account read access to the project, then:

    ```bash
    export BWS_ACCESS_TOKEN="0.48c7…"          # the machine account token, from Secrets Manager
    bws run --project-id <project-id> -- wp-ssh-bridge pull --silent
    ```

    `bws secret list <project-id> --output env` shows what the run will see. Keep `--project-id` on the command: without it, every secret the machine account can reach becomes a variable, and unrelated `WP_SSH_*` names from another project would win over your config file.

    Two things to avoid here. `--no-inherit-env` starts the command with an empty environment, which drops `PATH` and `SSH_AUTH_SOCK`, so the agent that signs the SSH connection disappears with it. And `bws run` does not mask secret values in output, so keep `--silent` on and do not print the environment from scripts.

  </Tab>
  <Tab title="Bitwarden Password Manager">

    The personal vault CLI, `bw`, has no run command and no projects; it hands out one value at a time. That is enough for the single real secret:

    ```bash
    export BW_SESSION="$(bw unlock --raw)"
    WP_SSH_CLONE_DB_PASSWORD="$(bw get password 'target database')" \
      wp-ssh-bridge clone --silent \
        --destination deploy@source.example.com \
        --remote-path /home/source/public_html \
        --db-host db.example.com --db-name target_db --db-user target_user
    ```

    Prefixing the variable to the command keeps it out of your shell's environment and history. For a whole set of variables per environment, Secrets Manager is the better fit.

  </Tab>
</Tabs>

## DDEV and wp-env

Nothing changes. The DDEV provider commands run on the host, so they see the environment of the `ddev pull` process, and wp-env projects run the CLI directly:

```bash
op run --environment <environment-id> -- ddev pull wp-ssh -y
bws run --project-id <project-id> -- npx wp-ssh-bridge pull --silent
```

## Several environments

Give each target its own Environment or project, and keep everything they share in the config file:

```bash
op run --environment <production-id> -- wp-ssh-bridge pull --silent
op run --environment <staging-id>    -- wp-ssh-bridge pull --silent
```

Where the variants hold no secrets at all, `--config-file .wp-ssh.staging.yaml` does the same job without a vault; see [several sites in one repository](/docs/configuration#monorepo) for the layout.

## CI

Both vendors ship a GitHub Action that resolves the same references with a non-interactive account, so a workflow reads like the local command:

<Tabs inline param="manager" syncKey="manager">
  <Tab title="1Password">

    ```yaml title=".github/workflows/pull.yml"
    - uses: 1password/load-secrets-action@v2
      with:
        export-env: true
      env:
        OP_SERVICE_ACCOUNT_TOKEN: ${{ secrets.OP_SERVICE_ACCOUNT_TOKEN }}
        WP_SSH_PULL_DESTINATION: op://Infrastructure/production-wordpress/ssh_destination
        WP_SSH_PULL_REMOTE_PATH: op://Infrastructure/production-wordpress/remote_path
    - run: npx wp-ssh-bridge pull --silent
    ```

    A service account also works with `op run --environment` in any other CI system; set `OP_SERVICE_ACCOUNT_TOKEN` and use the same command as locally.

  </Tab>
  <Tab title="Bitwarden Secrets Manager">

    ```yaml title=".github/workflows/pull.yml"
    - uses: bitwarden/sm-action@v2
      with:
        access_token: ${{ secrets.BWS_ACCESS_TOKEN }}
        secrets: |
          <secret-id> > WP_SSH_PULL_DESTINATION
          <secret-id> > WP_SSH_PULL_REMOTE_PATH
    - run: npx wp-ssh-bridge pull --silent
    ```

  </Tab>
</Tabs>

The SSH key itself still has to reach the runner, through an agent step or a deploy key, as for any job that opens an SSH connection. That part is unchanged by the secrets manager; [SSH access](/docs/ssh-access) describes what the CLI expects.

## When it does not work

| Symptom | Cause |
| --- | --- |
| `the destination already carries the user, host, and port` | The vault sets `WP_SSH_PULL_DESTINATION` while the config file, another variable, or a flag still sets `pull_user`, `pull_host`, or `pull_port`. Keep one form. |
| `Permission denied (publickey)` under `bws run` | `--no-inherit-env` removed `SSH_AUTH_SOCK`. Drop the flag. |
| A value shows as `<concealed by 1Password>` | Expected: `op run` masks secrets it injected. Use `--no-masking` only while debugging, never in CI logs. |
| The run prompts for a value | The variable is missing from the Environment or project, and the command ran without `--silent`, so `init`-style prompts appeared. Check with `op environment read` or `bws secret list --output env`, and keep `--silent`. |
| The wrong environment was pulled | Two Environments or projects both define `WP_SSH_PULL_DESTINATION`. Pass exactly one `--environment` or `--project-id`. |
