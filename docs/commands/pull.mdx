`pull` brings the remote site to you. It exports the source database with WP-CLI, downloads it, syncs the files, imports the database locally, rewrites every URL for your environment, and removes plugins that only belong on production.

It is the command you run before you start working, and again whenever the local copy has gone stale.

:::note[Reads from the source, writes locally]
A pull never modifies the source site. It creates a temporary database dump in the remote temp directory and deletes it again, including on failure. When the host has no usable WP-CLI, a `wp-ssh-bridge-wp-cli.phar` is also left in that directory for later runs. Everything else it changes is on your machine.
:::

## Run it

<Tabs inline param="integration" syncKey="integration">
  <Tab title="Standalone">

    In a plain WordPress checkout, `pull` uses the local `wp` binary. If none is available, a managed `wp-cli.phar` is downloaded into the project's scratch directory and used instead.

    ```bash
    wp-ssh-bridge pull --silent
    ```

    Everything the command needs comes from `.wp-ssh.yaml`, which [`init`](/docs/quickstart) writes. For a one-off source, pass it inline:

    ```bash
    wp-ssh-bridge pull --silent \
      --destination deploy@example.com \
      --remote-path /home/example/public_html
    ```

    The local WordPress root defaults to the project directory. Set `local_wp_path` when WordPress lives in a subdirectory such as `web` or `public`.

  </Tab>
  <Tab title="DDEV">

    A DDEV project can pull in two ways. Both rewrite URLs, align the table prefix, and clean up plugins; they differ in who drives the run.

    ```bash title="Native DDEV lifecycle"
    ddev pull wp-ssh -y
    ```

    ```bash title="Direct, easier to script"
    wp-ssh-bridge pull --silent
    ```

    The native command prints DDEV's lifecycle output and lets DDEV import the dump itself, so the local site is not put into maintenance mode. DDEV calls each provider step (database, files, post-pull) as a separate process, so each step authenticates on its own, and an SSH agent that asks for approval asks once per step. It takes no wp-ssh-bridge flags.

    The direct command runs the whole pipeline over one SSH connection, keeps the local site in maintenance mode from the import to the end of the run, and accepts every flag below. Without `--silent` or `--yes`, it prints the source and asks you to confirm. Use the native command for everyday interactive pulls, and the direct one in scripts or whenever you need a flag. How to call the binary depends on how you installed it; see [Running the CLI](/docs/installation#running-the-cli).

    Local WP-CLI runs as `ddev wp` inside the web container. The docroot, project URL, and temp directories come from `ddev describe`, so `init` fills them in for you.

    For a one-off override with the native command, use DDEV's inline environment:

    ```bash
    # Another source for this run only
    ddev pull wp-ssh \
      --environment=WP_SSH_PULL_DESTINATION=deploy@staging.example.com,WP_SSH_PULL_REMOTE_PATH=/home/staging/public_html \
      -y
    ```

    :::tip[Teams with individual SSH users]
    Commit a `~/.ssh/config` alias, such as `example-production`, as the destination in the versioned `.ddev/wp-ssh.yaml`, and let each developer map it to their own user in their `~/.ssh/config`. See [SSH access](/docs/ssh-access#aliases-resolve-through-ssh).
    :::

    After a pull, DDEV also learns the local hostnames derived from your domain mappings. They are written into `.ddev/config.yaml` as `additional_hostnames`, using DDEV's resolved TLD, so multisite domains resolve locally.

  </Tab>
  <Tab title="wp-env">

    The environment must be running, because the CLI reads the WordPress path and URL from `wp-env status --json` and runs WP-CLI inside the `cli` container.

    ```bash
    npx wp-env start
    wp-ssh-bridge pull --silent
    ```

    Three things work differently here, all handled automatically:

    - Local WP-CLI runs as `wp-env run cli wp --path=/var/www/html`. A host `wp` cannot reach the container database, whose port changes on every start.
    - The database dump is staged inside the tree wp-env mounts at `/var/www/html`, so the import runs against the container database. After a successful import the dump is deleted and a deny-all `.htaccess` is written beside it, because that directory is served over HTTP.
    - `wp-config.php` is preserved, never pulled. wp-env generates it with working local credentials. When the source uses another table prefix, the pull writes it into that file; if wp-env regenerates the file and WordPress shows the installer, pull again.

    :::warning[Mounted plugins and themes are skipped]
    If `.wp-env.json` declares `plugins`, `themes`, or `mappings`, wp-env bind-mounts those directories over `wp-content`. Files pulled into them would be shadowed by the mounts, and deleting a live mountpoint can fail, so those paths are excluded and the CLI warns before it starts. For production content only, sync the database alone:

    ```bash
    wp-ssh-bridge pull --silent --skip-files
    ```
    :::

    The Docker runtime is required. The experimental Playground runtime has no `wp-env run`, so preflight rejects it with a message telling you to restart with `--runtime=docker`.

  </Tab>
</Tabs>

## What happens, in order

<Steps>
  <Step title="Preflight">
    Local tools, SSH access, the paths on both sides, and WP-CLI are checked first, so a failure stops the run before anything changes. [How it works](/docs/how-it-works#preflight) lists every check.
  </Step>
  <Step title="Database export and download">
    `wp db export` on the source writes a gzipped dump of the WordPress installation's tables into the remote temp directory. Other sites or applications sharing the source database are [left out](/docs/how-it-works#safety-rules). The dump is downloaded, then removed remotely, and the cleanup is retried if the run fails.
  </Step>
  <Step title="File sync">
    rsync mirrors the source WordPress root into your local root with `--delete`, minus the exclusions below. Without rsync on either side, a tar archive is streamed over SSH instead, which cannot delete stale files, and the CLI says so.
  </Step>
  <Step title="Import">
    In DDEV mode, the copied `wp-config.php` is sanitised first, so the import reaches the DDEV database. The local site then goes into maintenance mode and the dump is imported. Maintenance mode stays on until the last step below has finished. Skip it with `--skip-maintenance-mode`. When no WordPress site is installed locally yet, as on a fresh project's first pull, there is nothing to protect and the import runs without it.

    After a successful import, the pull removes the local tables the pulled database does not contain, so nothing of the old local copy lingers, not even under another prefix. Which tables count is decided before the import, and a failed import removes nothing. `db_reset`, `WP_SSH_DB_RESET`, or `--db-reset` choose the scope:

    | Value | Effect |
    | --- | --- |
    | `database` | Every table the dump does not contain. The default in DDEV and wp-env, where the project's database belongs to that project alone, as with `ddev import-db`. |
    | `installation` | Only the tables of the installation the local `wp-config.php` describes. The default in standalone mode, where the database may be shared with other local sites. |
    | `none` | Nothing is removed; the pull reports how many tables it kept. |

    A native `ddev pull` hands the dump to DDEV, which imports it without maintenance mode and always empties the database first, whatever `db_reset` says.
  </Step>
  <Step title="Table prefix">
    The imported tables keep the source table prefix. When your local `wp-config.php` uses a different `$table_prefix`, for example `wp_` locally and `abc_` on the source, the local value is changed to the source prefix before anything loads WordPress. The tables are not renamed, so pushing back to the source keeps its prefix. Unless `db_reset` is `none`, the tables under the old local prefix were already removed in the import step.
  </Step>
  <Step title="URL rewrites">
    A WP-CLI search-replace runs for the site URL and every configured domain mapping, per blog on multisite, including the `site` and `blogs` tables. Hard-coded constants in `wp-config.php` such as `WP_HOME`, `WP_SITEURL`, and `DOMAIN_CURRENT_SITE` are rewritten too, so production values cannot override the imported database. wp-env is the exception: its generated `wp-config.php` already points at the local URL.
  </Step>
  <Step title="Plugin cleanup">
    Plugins on the block list that are actually installed are deactivated and deleted through WP-CLI. Skipped in wp-env projects with mounts, where those directories are your own working tree.
  </Step>
  <Step title="Page builder CSS">
    Page builders store generated CSS that still points at the old URLs after an import. The CLI runs `wp elementor flush-css`, `wp bricks regenerate_assets`, and `wp beaver clearcache` with plugins loaded, adding `--network` on multisite where the builder supports it. Builders that are not installed are skipped silently. A failure is reported as a warning and does not fail the pull. Skip the step with `--skip-cache-rebuild`.

    Maintenance mode is lifted after this step, or as soon as the import or a later step fails.
  </Step>
</Steps>

## What is excluded

File pulls skip paths that are either local-only or pointless to copy:

```text
.git/                              your repository
.ddev/                             local DDEV state, including its logs
.wp-ssh/                           the CLI's scratch directory
wp-config-ddev.php                 DDEV's generated config
wp-content/cache/                  page and object caches
wp-content/upgrade/                WordPress update staging
wp-content/updraft/                UpdraftPlus backups
wp-content/ai1wm-backups/          All-in-One WP Migration backups
wp-content/languages/wpml/queue/   WPML translation queue
wp-content/uploads/                unless --clone-images
*.log                              at any depth in the WordPress tree
blocked plugin directories         from the block list
```

`wp-config.php` is pulled and sanitised in DDEV mode, and preserved in standalone and wp-env mode, where the local file already carries working database credentials.

## Flags

| Flag | Effect |
| --- | --- |
| `--silent` | No prompts and no confirmation. Uses config, environment, and flags. The flag for scripts. |
| `--yes`, `-y` | Skip the source confirmation of a direct pull in a DDEV project. Standalone and wp-env pulls have no confirmation, and `--yes` does not skip their value prompts. |
| `--skip-files` | Database only. Useful when you just want fresh content. |
| `--skip-db` | Files only. |
| `--skip-import` | Downloads the database without importing it. Search-replace is skipped too. |
| `--clone-images` | Include `wp-content/uploads`. Off by default because media is usually the bulk of a site. |
| `--skip-search-replace` | Leave URLs untouched after the import. |
| `--skip-maintenance-mode` | Do not enable WordPress maintenance mode during the import. |
| `--skip-cache-rebuild` | Do not rebuild page builder CSS after the import. |
| `--db-reset` | Which tables to remove after the import when the dump does not contain them: `database`, `installation`, or `none`. Defaults to `database` in DDEV and wp-env and `installation` in standalone mode. |
| `--force-scp` | Use the tar-over-SSH transport even when rsync is available. |
| `--destination`, `--remote-path`, `--remote-tmp-dir` | Override the source for this run. `--destination` takes `user@host[:port]`, an `ssh://` URL, or a `~/.ssh/config` alias. |
| `--user`, `--host`, `--port` | The split form of the address, for configs that still use it. Not combinable with `--destination`. |
| `--local-wp-path`, `--local-url` | Override the local WordPress root and URL. |
| `--plugin-remove-file` | Use another plugin block list file for the cleanup. |
| `--config-file` | Read another YAML file, for example `.wp-ssh.production.yaml`. |
| `--project-root` | Run against a project other than the one the working directory belongs to. |
| `--integration` | Pin the runtime to `ddev`, `wp-env`, or `standalone`. |

## Common variations

```bash title="Just the content, no files"
wp-ssh-bridge pull --silent --skip-files
```

```bash title="A full copy including media"
wp-ssh-bridge pull --silent --clone-images
```

```bash title="A second source, such as staging"
# Keep a separate config file per source and select it per run.
wp-ssh-bridge pull --silent --config-file .wp-ssh.staging.yaml
```

```bash title="Inspect the dump before importing"
wp-ssh-bridge pull --silent --skip-files --skip-import
```

## When something fails

| Symptom | Cause | Fix |
| --- | --- | --- |
| `Permission denied (publickey)` | The source host does not accept your key. | Test `ssh <destination>` first; the CLI uses the same OpenSSH configuration. See [SSH access](/docs/ssh-access#when-a-connection-fails). |
| Remote path errors | `pull_remote_path` is not absolute or does not contain `wp-config.php`. | Set it to the absolute WordPress root on the source. |
| `mariadb-dump: command not found` | The host ships only the legacy MySQL client names, and the installed binary predates the workaround. | [Update the CLI](/docs/installation#updating). If preflight prints the compatibility line and the export still fails, the host lacks `mysqldump` as well. See [Netcup and MariaDB clients](/docs/troubleshooting/netcup-mariadb). |
| Local files not writable | Ownership or permissions on the local WordPress directory. | Fix them, then run again. The error names the exact path. |
| WordPress shows the installer after a pull | The local `$table_prefix` does not match the imported tables, and the CLI could not change it: `wp-config.php` has no `$table_prefix` line, as in Bedrock, or another file overrides it. The CLI warns about both. | Set the source prefix where your config defines it. |
| Tables the source no longer has remain after a pull | `db_reset` is `none`, or the CLI warned that it could not list the local tables or read the local `$table_prefix`, and left them in place. | Unset `db_reset` or choose `installation` or `database`, fix what the warning names, and pull again. |
| `scp/tar transport: stale local files not removed (no --delete equivalent)` | rsync is missing on one side, so the tar-over-SSH fallback is in use. | Install rsync on both machines, or accept that files removed on the source stay behind locally. |

More in [Troubleshooting](/docs/troubleshooting).
