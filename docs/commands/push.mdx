`push` is the reverse of a pull. It exports your local database, uploads it, imports it on the target, syncs your local WordPress tree to the target's WordPress root, and rewrites URLs on the target so the site answers under its own domain.

:::danger[Push overwrites the target]
The target database is replaced and its files are mirrored with `rsync --delete`. There is no undo. Confirm the host, the remote path, and the target URL before every push, and keep a backup of the target. Never point a push at production unless that is exactly what you mean to do.
:::

Check where a push will go before you run it: the push values in the config file, and `wp-ssh-bridge domains list` for the domain mappings. In a DDEV project, `ddev push` asks DDEV's usual question, and a direct push prints the resolved target and asks you to confirm; `--yes` or `--silent` skips that question. A standalone push has no confirmation step: without `--silent` it prompts for each push value, pre-filled from the config, and then starts. Reserve `--silent` for runs where the target is pinned in the config file.

## Run it

<Tabs inline param="integration" syncKey="integration">
  <Tab title="Standalone">

    The standard way to push. Your local checkout is the source of truth.

    ```bash
    wp-ssh-bridge push --silent
    ```

    With an inline target. On `push`, the short flags refer to the push target, so `--destination` means `--push-destination`:

    ```bash
    wp-ssh-bridge push --silent \
      --destination deploy@staging.example.com \
      --remote-path /home/staging/public_html \
      --push-url https://staging.example.com
    ```

    The explicit spelling works too and is clearer in scripts:

    ```bash
    wp-ssh-bridge push --silent \
      --push-destination deploy@staging.example.com \
      --push-remote-path /home/staging/public_html \
      --push-url https://staging.example.com
    ```

    `--push-user`, `--push-host`, and `--push-port` remain as the split form of the address for configs that still use it.

    Set `push_url` whenever you can. Without it the CLI reads the target's current home URL before the import and uses that, which works but relies on the target being in a sane state. On a target without an installed site, such as the first push into an empty directory, there is nothing to read, so the push stops before uploading anything until `push_url`, a push domain mapping, or `--skip-search-replace` says what to do with the URLs.

  </Tab>
  <Tab title="DDEV">

    A DDEV project can push through DDEV's own lifecycle or directly. Both import the database on the target, sync the files, and rewrite URLs there; they differ in who drives the run.

    ```bash title="Native DDEV lifecycle"
    ddev push wp-ssh -y
    ```

    ```bash title="Direct"
    wp-ssh-bridge push --silent
    ```

    The native command prints DDEV's lifecycle output and runs each provider step (database, files, post-push) as a separate process, so each step authenticates on its own. It does not put the target into maintenance mode and takes no wp-ssh-bridge flags. The direct command runs over one SSH connection, keeps the target in maintenance mode for the whole push, accepts every flag below, and asks you to confirm the resolved target unless you pass `--yes` or `--silent`.

    The local database is exported through `ddev wp`, so the container database is the source. Files come from your local WordPress root on the host.

    With the native command, override the target inline with DDEV's environment flag:

    ```bash
    ddev push wp-ssh \
      --environment=WP_SSH_PUSH_DESTINATION=deploy@staging.example.com,WP_SSH_PUSH_REMOTE_PATH=/home/staging/public_html,WP_SSH_PUSH_URL=https://staging.example.com \
      -y
    ```

    :::warning[DDEV files are local files]
    A push sends your local WordPress tree, not the container's. Make sure your working copy is what you want on the target: a half-finished plugin update or a stray vendor directory travels with it.
    :::

  </Tab>
  <Tab title="wp-env">

    **Push is rejected in wp-env projects.** The command exits with an error rather than running.

    The reason is the local file tree. wp-env manages the WordPress installation itself, uploads are excluded from pulls by default, and every `plugins`, `themes`, or `mappings` path declared in `.wp-env.json` is a Docker bind mount that is empty on the host. Pushing that tree with `rsync --delete` would erase exactly those directories on the target.

    ```text
    Error: push does not support wp-env projects; the local WordPress tree is managed by wp-env …
    ```

    :::danger[Do not work around it with `--integration`]
    Passing `--integration standalone` makes the CLI treat the directory as a plain WordPress root and bypasses this check. The push would then mirror empty mounted directories onto the target and delete the plugins, themes, and uploads that live there. There is no safe way to push from a wp-env project.
    :::

    **What to do instead:** push from a standalone checkout of the site. Clone the repository into a separate directory, run [`init`](/docs/quickstart) there with the target details, and push from that. Your wp-env project stays what it is good at, which is local development against a container.

  </Tab>
</Tabs>

## What happens, in order

<Steps>
  <Step title="Preflight">
    Local tools, SSH access to the target, the paths on both sides, and WP-CLI are checked first, and nothing is uploaded until all of it passes. [How it works](/docs/how-it-works#preflight) lists every check.
  </Step>
  <Step title="Maintenance mode on the target">
    The target site is put into maintenance mode for the whole operation, so visitors do not meet a half-imported database. It is lifted again afterwards, including on failure. Skip it with `--skip-maintenance-mode`. When no WordPress site is installed on the target yet, as on the first push into an empty directory, there is nothing to protect and the push runs without it.
  </Step>
  <Step title="Database export, upload, import">
    Your local database is exported with WP-CLI, uploaded to the remote temp directory, and imported there with remote WP-CLI. Before the import, the target's current URL is captured when `push_url` is not set.
  </Step>
  <Step title="File sync">
    rsync mirrors your local WordPress root onto the target's WordPress root, with the exclusions below. Without rsync, the tar-over-SSH fallback is used, which does not remove stale files.
  </Step>
  <Step title="URL rewrites on the target">
    A remote WP-CLI search-replace rewrites the local URL to the target URL, applies every configured push domain mapping, and updates the multisite `site` and `blogs` tables.
  </Step>
</Steps>

## What is never pushed

```text
wp-config.php         the target keeps its own database credentials
wp-config-ddev.php    DDEV's generated config
.ddev/                local DDEV state
.git/                 your repository
.wp-ssh/              the CLI's scratch directory, including the downloaded dump
```

That list is deliberately short. A push is meant to make the target match your local tree, so everything else, including `wp-content/uploads` and your plugins and themes, is sent.

## Flags

| Flag | Effect |
| --- | --- |
| `--silent` | No prompts and no confirmation. Only use it when the target is pinned in config. |
| `--yes`, `-y` | Skip the target confirmation of a direct push in a DDEV project. A standalone push has no confirmation, and `--yes` does not skip its value prompts. |
| `--skip-files` | Database only. |
| `--skip-db` | Files only. |
| `--skip-search-replace` | Do not rewrite URLs on the target. |
| `--skip-maintenance-mode` | Leave the target site reachable during the push. |
| `--force-scp` | Use the tar-over-SSH transport even when rsync is available. |
| `--push-destination`, `--push-remote-path`, `--push-remote-tmp-dir`, `--push-url` | The push target. On `push`, the short forms `--destination`, `--remote-path`, and `--remote-tmp-dir` are aliases for these. |
| `--push-user`, `--push-host`, `--push-port` | The split form of the address, aliased by `--user`, `--host`, and `--port` on `push`. Not combinable with a destination. |
| `--local-wp-path`, `--local-url` | Override the local WordPress root the push reads from and the local URL it rewrites. |
| `--config-file` | Read another YAML file, for example `.wp-ssh.staging.yaml`. |
| `--project-root` | Run against a project other than the one the working directory belongs to. |
| `--integration` | Pin the runtime to `ddev` or `standalone`. A wp-env project cannot push. |

## Domain rewrites in both directions

A push rewrites the local URL to the target URL and then applies every push domain mapping. `wp-ssh-bridge domains add` writes a pull mapping and its inverse push mapping in one go; [Domain mappings](/docs/configuration#domain-mappings) explains the format and why protocol-less domains are the safer choice for multisite.

## A safe staging workflow

<Steps>
  <Step title="Keep staging in its own config file">

    ```bash
    wp-ssh-bridge init --silent \
      --config-file .wp-ssh.staging.yaml \
      --push-destination deploy@staging.example.com \
      --push-remote-path /home/staging/public_html \
      --push-url https://staging.example.com
    ```

  </Step>
  <Step title="Check the target values">

    Read the push values back before anything is sent. A standalone push does not ask for confirmation.

    ```bash
    cat .wp-ssh.staging.yaml
    wp-ssh-bridge domains list --config-file .wp-ssh.staging.yaml
    ```

  </Step>
  <Step title="Push the files first">

    This is a real push: the files on the target are replaced, only the database is left alone. Check the site afterwards, then push the database. It splits a big change into two smaller ones.

    ```bash
    wp-ssh-bridge push --silent --config-file .wp-ssh.staging.yaml --skip-db
    ```

  </Step>
  <Step title="Push the database">

    ```bash
    wp-ssh-bridge push --silent --config-file .wp-ssh.staging.yaml --skip-files
    ```

  </Step>
  <Step title="Verify on the target">

    ```bash
    ssh deploy@staging.example.com "wp option get home --path=/home/staging/public_html"
    ```

    Then open the site in a browser and check a few internal links, which is where a missed domain mapping shows up first.

  </Step>
</Steps>

## When something fails

| Symptom | Cause | Fix |
| --- | --- | --- |
| `push does not support wp-env projects; …` | Expected in a wp-env project. | Push from a standalone checkout instead; see the wp-env tab above. |
| The target still shows the old or the local URL after a push | `push_url` was not set, so the push reused the target's home URL from before the import, and that value was wrong. | Set `push_url` and run again with `--skip-files`. |
| `the push target URL is unknown because it could not be read from the target` | A first push into an empty target has no URL to read, or the target's WP-CLI could not report it. | Set `push_url`, `WP_SSH_PUSH_URL`, or `--push-url`, add a push domain mapping, or pass `--skip-search-replace` to keep the local URLs. |
| Internal links point at the local domain | A push domain mapping is missing. | Add it with `domains add` and rerun the search-replace with `--skip-files`. |
| The target site stays in maintenance mode | The run was interrupted before cleanup. | Remove `.maintenance` in the target's WordPress root. |
| `scp/tar transport: stale remote files not removed (no --delete equivalent)` | rsync is missing on one side, so the tar-over-SSH fallback is in use and files removed locally remain on the target. | Install rsync on both machines. |

More in [Troubleshooting](/docs/troubleshooting).
