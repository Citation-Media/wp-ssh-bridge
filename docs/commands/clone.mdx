`clone` copies a site as a site, not as a development copy. Use it when the result should keep running as a real WordPress install: a migration to a new host, a production-shaped staging box, or a one-off duplicate.

The difference to [`pull`](/docs/commands/pull) is what it does *not* do. A clone skips the development rewrites and keeps everything a live site needs.

| | `pull` | `clone` |
| --- | --- | --- |
| Uploads and media | Only with `--clone-images` | Always included |
| `wp-config.php` | Sanitised for DDEV, preserved elsewhere | Copied, then target DB credentials written in |
| Production plugins | Deactivated and deleted | Kept |
| Development rewrites | Yes, including `WP_ENVIRONMENT_TYPE=development` | No |
| URL search-replace | Yes | Yes, from your configured mappings |
| Pre-existing target files | Mirrored with `--delete` | Kept, unless `--clean-target` |
| Tables of a previous installation | Kept and reported | Removed after the import |

:::warning[Standalone only]
`clone` refuses to run in a DDEV or wp-env project root. Both route WP-CLI through a container, so the import would land in the container database instead of the target you specified. Run it against a plain directory. For local onboarding, use [`pull`](/docs/commands/pull) instead.
:::

## Run it

<Tabs inline param="integration" syncKey="integration">
  <Tab title="Generic">

    This is the only supported runtime for `clone`. Run it from the directory that should become the new WordPress root, or point at one with `--project-root`.

    ```bash
    wp-ssh-bridge clone --silent \
      --destination deploy@source.example.com \
      --remote-path /home/source/public_html \
      --db-host db.example.com \
      --db-name target_db \
      --db-user target_user \
      --db-password target_password
    ```

    The source flags describe where to read from. The `--db-*` flags describe the database the cloned site will use once it lives on its new host. They are written into the copied `wp-config.php` before the database is imported, so the import and the finished site agree on the same credentials.

    Without `--db-prefix`, the target uses the source table prefix. With `--db-prefix`, the imported tables are renamed to that prefix after the import, together with the `user_roles` option of every site and the user meta keys WordPress derives from the prefix.

  </Tab>
  <Tab title="DDEV">

    **Clone is rejected in DDEV projects.**

    ```text
    Error: clone is not supported in DDEV projects
    ```

    Local WP-CLI runs as `ddev wp` in DDEV mode, so the database import would go into the DDEV container, not into the target database whose credentials you passed. The copied `wp-config.php` and the imported data would describe two different databases.

    **What to do instead:**

    - For a local development copy, use [`pull`](/docs/commands/pull), which is what DDEV mode is built for.
    - For a real migration, run `clone` from a plain directory outside the DDEV project. It can be anywhere on your machine; the result is a standalone WordPress tree you then move to the new host.

  </Tab>
  <Tab title="wp-env">

    **Clone is rejected in wp-env projects**, for the same reason as DDEV.

    ```text
    Error: clone is not supported in wp-env projects
    ```

    wp-env routes WP-CLI through `wp-env run cli`, so the import would target the container database rather than the credentials you passed with `--db-*`.

    **What to do instead:** use [`pull`](/docs/commands/pull) for local work, and run `clone` against a standalone target directory outside the wp-env project when you actually need a host-to-host copy.

  </Tab>
</Tabs>

## Required values

Source, exactly as for a pull:

| Flag | Config key | Environment variable |
| --- | --- | --- |
| `--destination` | `pull_destination` | `WP_SSH_PULL_DESTINATION` |
| `--remote-path` | `pull_remote_path` | `WP_SSH_PULL_REMOTE_PATH` |

`--destination` takes `user@host[:port]`, an `ssh://` URL, or a `~/.ssh/config` alias; the split `--user`, `--host`, and `--port` flags still work for configs that use them. See [SSH access](/docs/ssh-access).

Target database, written into `wp-config.php`:

| Flag | Config key | Environment variable |
| --- | --- | --- |
| `--db-host` | `clone_db_host` | `WP_SSH_CLONE_DB_HOST` |
| `--db-name` | `clone_db_name` | `WP_SSH_CLONE_DB_NAME` |
| `--db-user` | `clone_db_user` | `WP_SSH_CLONE_DB_USER` |
| `--db-password` | `clone_db_password` | `WP_SSH_CLONE_DB_PASSWORD` |
| `--db-prefix` (optional) | `clone_db_prefix` | `WP_SSH_CLONE_DB_PREFIX` |

:::tip[Keep the password out of version control]
Put the source and the non-secret target values in the config file, and pass the password through the environment:

```bash
export WP_SSH_CLONE_DB_PASSWORD='…'
wp-ssh-bridge clone --silent
```
:::

## Config mode

For a migration you run more than once, keep it in a file:

```yaml title=".wp-ssh.yaml"
pull_destination: "deploy@source.example.com"
pull_remote_path: "/home/source/public_html"

clone_db_host: "db.example.com"
clone_db_name: "target_db"
clone_db_user: "target_user"
clone_db_prefix: "wp_"

# The new site answers under a different domain, so rewrite it during the clone.
pull_domain_replacements:
  - old: "source.example.com"
    new: "target.example.com"
```

```bash
export WP_SSH_CLONE_DB_PASSWORD='…'
wp-ssh-bridge clone --silent
```

## Emptying the target first

A clone is **additive** by default. Files are added and updated, but whatever was already in the target directory stays: a hosting provider's placeholder `index.html`, a starter theme, an old install. On the rsync transport that means no `--delete`; the tar transport has no equivalent at all.

Pass `--clean-target` to start from an empty tree:

```bash
wp-ssh-bridge clone --silent --clean-target
```

:::danger[`--clean-target` deletes data]
It removes pre-existing content in the resolved target directory before the sync and cannot be undone. Print the resolved path and check it before you run this. On the rsync transport it adds `--delete`, keeping configured exclusions; on the tar transport it empties the target WordPress directory, preserving only operational entries such as `.git`, `.ddev`, `.wp-ssh`, `wp-config-ddev.php`, `.wp-ssh.yaml`, and the `wp-ssh-bridge` binary, and refusing to run against a filesystem root or a home directory.
:::

`--clean-target` exists only on `clone`. It is rejected on `pull` and `push`.

## The target URL

A clone moves the site to another domain only when you name one. Without a target URL, it keeps the source URL, which is what a migration to a new host under the same domain needs:

```text
• Keeping the source site URL: no target URL is configured. Set local_url, WP_SSH_PULL_LOCAL_URL, or --local-url, or add a pull domain mapping, to move the clone to another domain.
```

To move the site, name the target with `local_url`, `WP_SSH_PULL_LOCAL_URL`, or `--local-url`, or with a domain mapping such as `source.example.com` to `target.example.com`. The database is rewritten, and the `WP_HOME`, `WP_SITEURL`, and `DOMAIN_CURRENT_SITE` constants get the same replacements, but only where the copied `wp-config.php` already defines them. A `WP_SITEURL` in a subdirectory keeps its path, and a site that keeps its URLs in the database gets no new constants.

## Replacing an existing installation

A clone makes the imported database the target's only WordPress installation. The import itself only replaces the tables the dump contains, so after it the clone removes the tables a previous installation left behind:

- tables under the prefix the cloned site uses that the dump did not create, such as plugin tables of the old site, and
- tables under the prefix the target's previous `wp-config.php` used, when that config pointed at the same database.

Tables under other prefixes stay, and so does another WordPress installation whose prefix merely starts with the same characters, such as `wp_shop_` next to `wp_`. Shared hosting often gives one database to several sites, so the clone never resets the whole database.

```text
✓ Previous installation tables removed
```

## Maintenance mode during the import

When a WordPress site is already installed at the target, the clone puts it into maintenance mode while the database is imported and lifts it again afterwards, including on failure. A migration usually targets an empty directory and a new database instead. There is no site to protect then, and WP-CLI could not activate maintenance mode anyway, so the import runs without it:

```text
• Skipping local maintenance mode: no installed WordPress site at the destination yet
```

With `--clean-target`, the previous site is replaced, so maintenance mode is skipped without checking:

```text
• Skipping local maintenance mode: --clean-target replaces the destination site
```

## Migrating a site

[Migrate a site](/docs/migrate-a-site) walks through a complete move to a new host, either by running `clone` on the new server, which then connects to the old one, or through your own machine followed by a [`push`](/docs/commands/push). The CLI always runs on the machine that receives the site; the old host never sends to the new one directly.

## When something fails

| Symptom | Likely cause and fix |
| --- | --- |
| `clone is not supported in DDEV projects` | You are inside a DDEV or wp-env project. Run it from a plain directory. |
| `unknown command "clone"` | The binary predates the rename from `migrate`. [Update it](/docs/installation#updating). |
| `unknown config key "migrate_db_host"` | Old config keys. Rename `migrate_db_*` to `clone_db_*`. |
| Target DB credentials reported as missing | Old `WP_SSH_MIGRATE_DB_*` variables are ignored. Rename them to `WP_SSH_CLONE_DB_*`. |
| The cloned site shows the source domain | No target URL or domain mapping was configured, or `--skip-search-replace` was set. The clone keeps the source URL by design; set `local_url` or add the mapping and rerun. |
| The cloned site redirects to `localhost` | The binary predates keeping the source URL, and `wp-config.php` got `WP_HOME` and `WP_SITEURL` set to `https://localhost`. [Update it](/docs/installation#updating), then remove those defines or set them to the real URL. |
| Old files from the previous install remain | Clones are additive for files. Use `--clean-target` if that is what you want. |
| Old tables from the previous install remain | The previous `wp-config.php` pointed at another database, or its prefix or database name is not a plain string, so the clone could not tell they belong to it. Drop them manually. |
| `cannot rename … for --db-prefix` | The source database already holds tables under the `--db-prefix` prefix, so renaming would overwrite them. Choose another prefix or omit `--db-prefix`. |
| `Enabling local maintenance mode failed` with `The site you have requested is not installed` | The binary predates skipping maintenance mode on an empty target. [Update it](/docs/installation#updating), or pass `--skip-maintenance-mode` for this run. |

More in [Troubleshooting](/docs/troubleshooting).
